# 仕組み

ソースから DDL までの間でコンパイラが何をしているか。動かし方は
[ガイド](guide.md) にあります。ここは中身の話です。

## パイプライン

```text
source
 → lexer      改行が文を終える。eval(...) は括弧を数えて丸ごと持ち上げるので、
              SQL が DSL の字句解析器に届くことはない
 → parser     手書きの再帰下降。行の切れ目で復帰するので、
              1回の実行で見つけられるエラーを全部報告できる
 → resolver   blueprint 展開 → mixin 展開 → 関連の解決 → 名前の導出
 → ir         mixin と blueprint は消え、名前は全部確定している
 → codegen    選ばれた出力先の DDL
```

どの段も次の段に、より小さい問題を渡します。codegen まで来ると適用すべき規約は
残っておらず、名前の確定したテーブル・カラム・制約だけがあります。

## 解決の順序

`use` が書かれた位置で展開され、次に `except` が取り除き、最後に `override` が
差し替えます。順序を固定してあるので、それらの文をブロックのどこに書いたかで
結果が変わることはありません。

カラムの順序だけは例外で、これは意図的です。カラムは宣言した順に DDL へ出ます。
その順序は書き手が選んだものだからです。

`belongs_to` は宣言した位置で外部キー列を予約しますが、型は空けておきます。
型は参照先の主キーが分かってから埋まります。この2段階が無いと、外部キーは
書いた場所ではなく、どのテーブルでも末尾に溜まることになります。

## 名前

生成される名前は必ず `naming` のテンプレートを通り、テンプレートは必ず
`nouns` の辞書を通して名詞を解決します。抜け道はありません。出力に名前が
現れたなら、それはテンプレートと名詞から来ています。

名詞はソースでは識別子として書かれ、そこから単数形・複数形・略語という語形に
解決されます。識別子はキーであって、それ以上のものではありません。出力に出るのは
単数形へ写されたときだけで、それは `singular=` を省いた場合に起きます。

`noun(a, b, ...)` は文字列ではなく複合名詞を作ります。文脈が求める数を取るのは
最後の要素だけなので、同じ式が `has_one` では `sent_message`、`has_many` では
`sent_messages` になります。`short()` だけは最後の要素ではなく全要素を置き換えます。
略語は数ではないからです。

## 診断

エラーが出ても実行は止まりません。1行1文の文法なので、パーサは失敗した行を
飛ばして次から拾い直せます。1回の実行で、届く範囲を全部報告します。

警告は「何かは作れるが、たぶん作るべきではない」場合です。規則的な活用に
落ちた名詞、主キーの無いテーブル、`except` で消された外部キー列、出力先が
保てる長さを超えた識別子などです。

最後のものは、うるさくても出す価値があります。PostgreSQL は 63 バイトで
何も言わずに切り詰めるので、切り詰めた2つが同じ名前だと分かるまで、
何も起きないからです。

## WebAssembly

`nounsql-core` の依存は `indexmap` だけで、I/O をしません。そのまま `wasm32`
にコンパイルできます。[プレイグラウンド](playground.html) と
[npm パッケージ](https://www.npmjs.com/package/nounsql) はどちらもそのビルドで
動いています。CLI と同じ字句解析器・解決器・コード生成器です。

このサイトのシンタックスハイライトも同じところから来ています。コードブロックの
色付けは JavaScript の別実装ではなくコンパイラ自身の字句解析器がやるので、
ハイライトが文法からずれることがありません。

## 制約付きデコード用の文法

[`nounsql.gbnf`](nounsql.gbnf) は llama.cpp 系の制約付きデコード用の GBNF 文法です。
言語モデルに NounSQL を生成させるとき、構文の内側に留めます。
